# Study notes

Short answers to say out loud, each with the place in this repo that shows it.
Paths are relative to the repo root; `Web/` is short for `DonationTracker.Web/`.

## MVC

"MVC splits a request into three parts. The controller receives the request and
decides what to do, the model carries the data, and the view turns that model
into HTML. In my app the Donations controller asks the service for the data,
puts it in a view model and hands it to the Razor view."

Where: `Web/Controllers/DonationsController.cs` line 18 (the `Index` action) and
line 26 (`return View(model)`). The route that maps URLs to controllers is
`Web/Program.cs` line 33.

## Razor tag helpers

"Tag helpers are attributes like `asp-for` and `asp-action` that run on the
server and generate the right HTML. `asp-for` gives an input its name, id, value
and validation attributes from the model property, so the form and the model
cannot drift apart. They read like HTML, which is why I prefer them to the older
`Html.` helpers."

Where: `Web/Views/Donations/Create.cshtml` line 11 (`asp-action`), line 15
(`asp-for` with `asp-items` for the supporter dropdown) and line 23
(`asp-validation-for`).

## Model validation

"I validate in three places. Data annotations on the model state the rules
once; the browser enforces them through jQuery validation for quick feedback;
and the controller checks `ModelState.IsValid` because the client can never be
trusted. Rules that need data or the clock, like 'not in the future' and 'the
supporter must exist', live in the service."

Where: annotations at `Web/Models/Donation.cs` line 13 (`Range`) and
`Web/Models/Supporter.cs` line 15 (`EmailAddress`); server check at
`Web/Controllers/DonationsController.cs` line 41; client scripts at
`Web/Views/Donations/Create.cshtml` line 37; service rules at
`Web/Services/DonationService.cs` lines 109 and 115.

## EF Core migrations

"A migration is a C# file that describes a schema change, generated by comparing
my entity classes with the last snapshot. Applying it runs the SQL and records
the migration in a history table, so every environment can be brought to the
same schema in order. I kept one migration, InitialCreate, which makes both
tables, the foreign key and an index on the foreign key."

Where: `Web/Migrations/20261001232457_InitialCreate.cs` lines 14 and 29
(`CreateTable`) and line 50 (`CreateIndex`). The context is registered at
`Web/Program.cs` line 10.

## DI lifetimes

"There are three lifetimes. Singleton is one instance for the whole app, scoped
is one per HTTP request, and transient is a new one every time it is asked for.
I registered the repository and service as scoped because they depend on the
DbContext, which is itself scoped; a singleton holding a DbContext would share
one context across requests, which is not thread-safe."

Where: `Web/Program.cs` lines 13 and 14 (`AddScoped`).

## The repository/service split

"The repository is the only class that talks to the DbContext; it just loads and
saves. The service holds the business logic and only knows the repository
interface. That separation is what lets me unit test the logic with a fake
repository and no database."

Where: the interface at `Web/Data/IDonationRepository.cs` line 5; the service
taking it in its constructor at `Web/Services/DonationService.cs` line 12; the
campaign total computed in the service at line 81.

## NUnit + Moq

"NUnit is the test framework: `[Test]` marks a test and `Assert.That` checks the
result. Moq builds a fake `IDonationRepository`, so I can tell it what to return
and then verify how it was called. For example, I check a valid donation calls
the repository's add method exactly once, and a future-dated one throws and
never calls it."

Where: `DonationTracker.Tests/DonationServiceTests.cs` line 18 (creating the
mock), line 31 (`Setup(...).ReturnsAsync`), line 59 (`Assert.ThrowsAsync`) and
line 91 (`Verify(..., Times.Once)`).

## Stored procedure vs LINQ

"LINQ through EF Core is my default: it is type-checked, lives with the code and
is easy to change. A stored procedure makes sense when the query is
performance-critical, when a DBA needs to tune it without a deployment, or when
access is granted to procedures rather than tables. The cost is logic living in
two places."

Where: the procedure at `sql/02_usp_GetDonationsBySupporter.sql` line 5; a
comparable LINQ query at `Web/Data/DonationRepository.cs` line 49.

## Index and execution plan

"I ran the procedure with STATISTICS IO and the actual plan before and after
adding an index. Before, SQL Server did an index seek on the foreign key index,
then a key lookup for every row and a sort: 402 logical reads. After adding a
covering index on SupporterId and DonatedOn descending, including Amount, it was
a single index seek with 4 logical reads, and the lookup and sort were gone."

Where: the index at `sql/03_ix_Donation_SupporterId_DonatedOn.sql` line 8; the
measured figures at `sql/PLAN-NOTES.md` line 11; the plans in `sql/plans/`.

## DTO vs entity

"An entity mirrors a database table; a DTO is the shape I choose to send over
the wire. Returning entities from an API leaks the schema, can expose fields I
did not mean to share and can loop through navigation properties when
serialised. So the service maps each Donation to a DonationDto by hand, with the
supporter's name flattened in."

Where: `Web/Models/DonationDto.cs` line 5; the hand mapping at
`Web/Services/DonationService.cs` line 60.

## REST conventions

"REST uses nouns for resources and HTTP verbs for actions. So reading the
collection is `GET /api/donations`, and it returns 200 with JSON. If I extended
it, `GET /api/donations/5` would return one item or 404, and `POST
/api/donations` would create one and return 201 with a Location header."

Where: `Web/Controllers/DonationsApiController.cs` line 8 (the route), line 19
(`HttpGet`) and line 23 (`return Ok(...)`). Only the GET exists in this repo.
