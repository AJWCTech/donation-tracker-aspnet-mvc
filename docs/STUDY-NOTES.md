# Study notes

Paths are relative to the repo root; `Web/` is short for `DonationTracker.Web/`.

## MVC

"MVC splits a request into three parts. The controller receives the request and
decides what to do, the model carries the data, and the view turns that model
into HTML. In my app the Donations controller asks the service for a page of
donations and the total, puts them in a view model and hands it to the Razor
view."

Where: `Web/Controllers/DonationsController.cs` line 27 (the `Index` action) and
line 35 (`return View(model)`). The route that maps URLs to controllers is
`Web/Program.cs` line 46.

## Razor tag helpers

"Tag helpers are attributes like `asp-for` and `asp-action` that run on the
server and generate the right HTML. `asp-for` gives an input its name, id, value
and validation attributes from the model property, so the form and the model
cannot drift apart. They read like HTML, which is why I prefer them to the older
`Html.` helpers."

Where: `Web/Views/Donations/Create.cshtml` line 11 (`asp-action`), line 15
(`asp-for` with `asp-items` for the supporter dropdown) and line 23
(`asp-validation-for`).

## Model validation

"I validate in three places. Data annotations on the model state the rules
once; the browser enforces them through jQuery validation for quick feedback;
and the controller checks `ModelState.IsValid` because the client can never be
trusted. Rules that need data or the clock, like 'not in the future' and 'the
supporter must exist', live in the service."

`Web/Models/Supporter.cs` line 15 (`EmailAddress`); server check at
`Web/Controllers/DonationsController.cs` line 50; client scripts at
`Web/Views/Donations/Create.cshtml` line 39; service rules at
`Web/Services/DonationService.cs` lines 242 and 248.

## EF Core migrations

"A migration is a C# file that describes a schema change, generated by comparing
my entity classes with the last snapshot. Applying it runs the SQL and records
the migration in a history table, so every environment can be brought to the
same schema in order. I have five: the two tables, the covering index, the
Identity tables, the stored procedure as raw SQL, and the audit table."

Where: `Web/Migrations/20261001232457_InitialCreate.cs` lines 14 and 29
(`CreateTable`); `Web/Migrations/20261001234805_AddDonationSupporterDateIndex.cs`
line 17 (`CreateIndex`);
`Web/Migrations/20261002001157_AddDonationsBySupporterProcedure.cs` line 16
(`migrationBuilder.Sql`). The context is registered at `Web/Program.cs` line 11.

## DI lifetimes

"There are three lifetimes. Singleton is one instance for the whole app, scoped
is one per HTTP request, and transient is a new one every time it is asked for.
I registered the repository and service as scoped because they depend on the
DbContext, which is itself scoped; a singleton holding a DbContext would share
one context across requests, which is not thread-safe."

Where: `Web/Program.cs` lines 25 and 26 (`AddScoped`).

## The repository/service split

"The repository is the only class that talks to the DbContext; it just loads and
saves. The service holds the business logic and only knows the repository
interface. That separation is what lets me unit test the logic with a fake
repository and no database."

Where: the interface at `Web/Data/IDonationRepository.cs` line 5; the service
taking it in its constructor at `Web/Services/DonationService.cs` line 13; the
paging rules in the service at line 101.

## NUnit + Moq

"NUnit is the test framework: `[Test]` marks a test and `Assert.That` checks the
result. Moq builds a fake `IDonationRepository`, so I can tell it what to return
and then verify how it was called. For example, I check a valid donation calls
the repository's add method exactly once, and a future-dated one throws and
never calls it."

Where: `DonationTracker.Tests/DonationServiceTests.cs` line 18 (creating the
mock), line 25 (`Setup(...).ReturnsAsync`), line 90 (`Assert.ThrowsAsync`) and
line 122 (`Verify(..., Times.Once)`).

## Unit tests vs integration tests

"Unit tests check one class with its dependencies faked, so they are fast and
pinpoint logic errors. Integration tests check that real pieces work together.
Mine run the real repository against a real LocalDB database built from the
migrations, which proves things a mock cannot: that the LINQ translates to SQL,
that SUM over no rows gives zero, and that paging returns the newest rows first."

Where: `DonationTracker.Tests/DonationRepositoryIntegrationTests.cs` line 34
(the database is created with `Migrate()`), line 97 (empty total), line 130
(paging order) and line 146 (the stored procedure).

## Stored procedure vs LINQ

"LINQ through EF Core is my default: it is type-checked, lives with the code and
is easy to change. A stored procedure makes sense when the query is
performance-critical, when a DBA needs to tune it without a deployment, or when
access is granted to procedures rather than tables. The cost is logic living in
two places."

Where: the procedure at `sql/02_usp_GetDonationsBySupporter.sql` line 5, called
by the app at `Web/Data/DonationRepository.cs` line 83; LINQ that becomes
`SELECT SUM(Amount)` in the same file at line 56.

## SQL injection

"SQL injection happens when user input is pasted into the SQL text, so the input
can change the query. The fix is to send values as parameters, never as text.
EF Core's LINQ queries are parameterised for me. Where I call the stored
procedure myself I use `FromSqlInterpolated`, which looks like string
interpolation but turns each value into a SQL parameter."

Where: `Web/Data/DonationRepository.cs` line 83.

## Index and execution plan

"I ran the procedure with STATISTICS IO and the actual plan before and after
adding an index. Before, SQL Server did an index seek on the foreign key index,
then a key lookup for every row and a sort: 402 logical reads. After adding a
covering index on SupporterId and DonatedOn descending, including Amount, it was
a single index seek with 4 logical reads, and the lookup and sort were gone. I
then moved that index into an EF migration so the model and database agree."

Where: the measured figures at `sql/PLAN-NOTES.md` line 11 and the plans in
`sql/plans/`; the index in the model at `Web/Data/AppDbContext.cs` line 30.

## Paging

"Returning every row does not scale, so the list and the API return one page at
a time. The repository uses Skip and Take with a fixed sort order, and the
service works out the total number of pages and moves an out-of-range page
number to the nearest valid one. Sorting by date and then Id matters: without a
tie-breaker a row could appear on two pages."

Where: `Web/Data/DonationRepository.cs` line 72 (`Skip`/`Take`);
`Web/Services/DonationService.cs` line 101 (total pages).

## DTO vs entity

"An entity mirrors a database table; a DTO is the shape I choose to send over
the wire. Returning entities from an API leaks the schema, can expose fields I
did not mean to share and can loop through navigation properties when
serialised. So the service maps each Donation to a DonationDto by hand, with the
supporter's name flattened in."

Where: `Web/Models/DonationDto.cs` line 5; the hand mapping at
`Web/Services/DonationService.cs` line 137; the paged wrapper at
`Web/Models/DonationPageDto.cs` line 4.

## REST conventions

"REST uses nouns for resources and HTTP verbs for actions. So reading the
collection is `GET /api/donations`, it returns 200 with JSON, and paging is done
with query string parameters. If I extended it, `GET /api/donations/5` would
return one item or 404, and `POST /api/donations` would create one and return
201 with a Location header."

Where: `Web/Controllers/DonationsApiController.cs` line 8 (the route), line 19
(`HttpGet`) and line 23 (`return Ok(...)`). Only the GET exists in this repo.

## Authentication and authorization

"Authentication is proving who you are; authorization is deciding what you may
do. I use ASP.NET Core Identity: it stores users with hashed passwords and signs
them in with a cookie. The controllers are marked `[Authorize]`, with
`[AllowAnonymous]` on the list actions, so anyone can view but only signed-in
staff can add or edit. After sign-in I only redirect to a local URL, to prevent
open-redirect attacks."

Where: `Web/Program.cs` line 15 (`AddIdentity`) and line 41
(`UseAuthentication`); `Web/Controllers/DonationsController.cs` lines 10 and 26;
`Web/Controllers/AccountController.cs` line 33 (`PasswordSignInAsync`) and line
45 (`IsLocalUrl`); the staff account is created at `Web/Data/StaffSeeder.cs`
line 35.

## Audit trail and transactions

"Every add and edit writes an audit row: who, when, which record, and the old
and new values. The service builds the entry because it knows what changed; the
repository saves the change and the entry in one database transaction, so either
both are saved or neither is. For a new row I need an explicit transaction,
because the Id is only known after the first save. Rows are insert-only."

Where: `Web/Data/DonationRepository.cs` lines 94 to 103 (the transaction);
`Web/Services/DonationService.cs` line 195 (old and new amount) and line 203
(building the entry); the signed-in user at
`Web/Controllers/DonationsController.cs` line 18; the test at
`DonationTracker.Tests/DonationServiceTests.cs` line 188.

## Continuous integration

"CI means every push is built and tested automatically, so a broken change is
caught straight away instead of by the next person. My workflow is a YAML file
in the repository: check out, install the SDK, restore, build, start LocalDB,
run the tests. It runs on a Windows runner because the integration tests need
LocalDB. I also wrote the Azure Pipelines version, but that one has not been
run."

Where: `.github/workflows/ci.yml` line 12 (the runner) and line 33 (the test
step); the Azure sketch is `azure-pipelines.yml`.
